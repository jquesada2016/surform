The linter

surform lint is the advisory pass: warnings about files that are legal but suspicious. Findings never change what check and build emit — but like a clippy step, surform lint exits 1 when anything fires, so it drops straight into CI:

sh
surform lint schema.surdl && surform build schema.surdl > schema.surql

Findings render exactly like diagnostics — code, snippet, help line, or --json — at warning severity. Codes are SDL-Lxxxx; this page is the catalog.

A reference to something no file defines — here a typo'd table in a permission filter (orgs for org; SurrealDB's catalog is flat, so the schema stays legal — the warning is the catch):

The reference warnings stay conservative on purpose: a param read in a permission or default can be bound by the client at query time, so only fn:: bodies (whose context the engine isolates from client-bound values) flag unknown params — a param definition resolves inside a body, and so do the session params and the record trio on a document-bound call. mod:: calls are covered by their module definitions, silo::/ml:: names by their version tails, and builtin paths (like an api middleware head named string::uppercase) resolve without any definition.

Ordering is not a lint subject: the compiler owns emission order — definitions may stand anywhere, a true cycle is the SDL-E0015 diagnostic, a dependency that crosses a scope-section boundary is SDL-E0016, and a duplicate definition is SDL-E1062 (see Who owns the order). The linter's remaining reference concern is the one the compiler cannot decide: a target that nothing in the document defines.

Suppressing a warning at its site

A deliberate exception does not need to live with the noise: a // surform-lint-allow: comment names the codes it excuses, and it excuses them on ONE statement — the statement it precedes (a same-line comment after the ; works too, the one-liner's natural home):

The allow is statement-scoped, not file-wide — moved onto another statement, it excuses nothing:

The orders table warns — its statement carries no allow. Codes are comma-listed on one line (// surform-lint-allow: SDL-L0001, SDL-L0006), and the comment rides its anchor through fmt and normalize, so the suppression survives reformatting. The same-line form after a one-liner's ;:

A typo'd code suppresses nothing, so it gets its own warning instead of silence:

SDL-L0099 is not a code — the linter reports SDL-L0023 at the comment, and the table's SDL-L0001 stands (only registered codes suppress). Misspelled markers (surform-lint-alow:) and allow comments with no statement after them report SDL-L0023 too. Two limits are by design: a REGISTERED code that fires nothing on its statement stays silent (it may be guarding a future change), and findings the file carries no statement for (an adoptee-only table under --info) have no site to excuse — they never suppress. SDL-L0023 itself cannot be allowed away.

On a composition root the allow stays file-scoped: it excuses findings in its own file only, even though the other files' spans overlap numerically. Findings render against the file they came from.

Resolved state, not source text

Some warnings only make sense once the database's state is available. With --info tags, lint evaluates the resolved state — the merged, placed, elided file — so a table the database itself holds wide open warns even though the schema file never spells a permissions clause: the reader adopts the stored PERMISSIONS FULL into the merged file, and SDL-L0001 evaluates that:

sh
surform lint schema.surdl --info db=acme/shop=info-db.txt
