Access (sign-in & tokens)

Accesses are SurrealDB's authentication schemes: they define how tokens are verified and, for your application's end users, how accounts sign up and sign in. Three kinds exist, chosen with type: — record, jwt, and bearer.

Record access: your app's users

The most common kind. A record access turns an email-and-password pair into a record user — SurrealDB runs your SurrealQL to create the account (signup) and to check a sign-in (signin):

No trailing ; inside those captures — the clause's value must be the returned result. $email and $password are what the client sends to the SIGNUP/SIGNIN endpoints.

JWT access: verify tokens from somewhere else

The jwt kind does not issue anything (unless given an issuer) — it verifies tokens. The verification source is either a JWKS url: or an algorithm: + key: pair:

One rule governs which keys you may write:

  • Asymmetric verify keys (es*, eddsa, rs*, ps*) are public keys — freely authorable, printed verbatim by the database.
  • Symmetric verify keys (hs*) and every issuer key are secrets. The database redacts them in INFO, and Surform accepts exactly one spelling there: the literal '[REDACTED]'. Writing a real key in those slots is a parse error:

That is deliberate: your schema file lives in git, so secret material must be provisioned outside it — that access class is applied manually, once.

Context: data for the session (SurrealDB 3.3)

context: evaluates at authentication and becomes $session.data — a way to pin per-session facts your queries can read. It requires an access method that authenticates a record (a record access, or a bearer for records), and the expression must be read-only:

Duration defaults

The three duration sides default to grant 30d, token 1h, session unlimited — and an access without a duration block round-trips to one without. A verify-only access (no issuer) can't issue tokens, so a declared token: side there is dropped by the engine — the linter catches it (SDL-L0011).
